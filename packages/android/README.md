# Osonai for Android

The Osonai chat for a native Android host app (a customer company's app that has the Osonai SDK inside). It is
an Android library (Kotlin, minSdk 24) with two parts:

- `Osonai`: the config, the host app's tool functions, what is on screen (`context`), `send`, `reset`, `release` and the callbacks.
- `OsonaiChatView`: the chat screen, a `FrameLayout` with an `android.webkit.WebView`.

The chat screen, the agent loop and the connection to the Osonai server are one HTML file in the library
(`osonai/src/main/assets/osonai/osonai-chat.html`, generated by `packages/embed`). The host app adds only its
own tool functions. They run in the host app, with the host app's own signed-in user token. The token never
goes to the chat page. The bridge protocol is in `docs/mobile.md`.

Coordinates: `com.github.zohidjon-m:osonai:0.1.0` on [JitPack](https://jitpack.io/#zohidjon-m/osonai). It depends
on `kotlinx-coroutines-android` 1.9.0 (as `api`) and `kotlin-stdlib` 2.1.20.

## Install

1. In your app's `settings.gradle.kts`, add JitPack:

   ```kotlin
   dependencyResolutionManagement {
       repositories {
           google()
           mavenCentral()
           maven("https://jitpack.io")
       }
   }
   ```

2. In your app module's `build.gradle.kts`:

   ```kotlin
   dependencies {
       implementation("com.github.zohidjon-m:osonai:0.1.0")
   }
   ```

**From source:** `cd packages/android && ./gradlew :osonai:publishToMavenLocal` (JDK 17) writes
`ai.osonai:osonai-android:0.1.0` to Maven Local; add `mavenLocal()` to your repositories and use those coordinates.

The steps that built Bozor, our test app, in `examples/shop/android` (Android Gradle Plugin 8.11.0, Kotlin
2.1.20, Gradle 8.14.3, compileSdk 35):

```sh
cd examples/shop/android
./gradlew assembleDebug
adb -s <device id> install -r app/build/outputs/apk/debug/app-debug.apk
```

### Network settings

The chat page calls the Osonai server from inside the WebView. Over **https**, the host app needs no setting.

To reach an **http** Osonai server (a test server on the local network), set this in your app's
`AndroidManifest.xml`. Use it for a test build only:

```xml
<application android:usesCleartextTraffic="true" ...>
```

The host app needs `android.permission.INTERNET`; the library manifest declares it, so it merges into the host
app.

The chat page loads from `file:///android_asset/osonai/osonai-chat.html`, so its origin is `null`. The Osonai
server must answer CORS with `Access-Control-Allow-Origin: *` (`npm run serve -- --cors '*'`). The view keeps `allowFileAccess` at its default (`false` on Android 11 and later): asset URLs
load without it.

## Usage

Create one `Osonai` after the user signs in, and register a function for each tool of the manifest. Use it from
the main thread.

```kotlin
import ai.osonai.Osonai
import ai.osonai.OsonaiChatView
import ai.osonai.OsonaiConfig
import ai.osonai.OsonaiTheme

val osonai = Osonai(OsonaiConfig(
    runtimeUrl = "https://osonai.example.com",
    appKey = "osk_pub_…", // the app's publishable key
    manifestJson = assets.open("manifest.json").bufferedReader().use { it.readText() },
    title = "Bozor assistant",
    greeting = "Hi! I can search products, manage your cart and check orders.",
    suggestions = listOf("Find red sneakers", "What is in my cart?"),
    placeholder = "Type a message",
    theme = OsonaiTheme(primary = "#0F766E", mode = OsonaiTheme.Mode.SYSTEM),
    showClose = true,
))

// args: the arguments after the Harness validated, resolved and bound them (app-function names).
osonai.tool("add_to_cart") { args -> api.addToCart(args.getString("productId"), args.optInt("quantity", 1)) }
osonai.tool("view_cart") { api.getCart() }

osonai.context = mapOf("current_screen" to "product", "current_product_id" to "p_106", "current_product_name" to "Ceramic Teapot")
osonai.onTurnEnd = { text, tools -> refreshCart() }   // tools: the names of the tools that ran
osonai.onClose = { closeChat() }
osonai.onError = { message -> Log.w("Chat", message) }

// Show the chat full screen, between the system bars (see "Known limits").
setContentView(FrameLayout(this).apply {
    fitsSystemWindows = true
    addView(OsonaiChatView(this@MainActivity, osonai))
})

osonai.send("What is in my cart?")   // as if typed; waits for the page when it is not ready yet
osonai.reset()                       // a new conversation

override fun onDestroy() {
    osonai.release()                 // the chat ends: cancel running tool functions, destroy the WebView
    super.onDestroy()
}
```

### Who owns the view

- The host app owns the `OsonaiChatView`. `Osonai` keeps only a weak reference to it, so an `Osonai` that lives
  longer than the Activity does not keep the view or the Activity.
- The host app can take the view off screen and add it again (the test app does this on `Close`). Tool functions
  keep running while it is off screen, and the conversation stays.
- Call `osonai.release()` once, when the chat ends for good: in `onDestroy` of the Activity that created the
  `Osonai`, or in `onCleared` of a ViewModel that holds it. It cancels the tool functions that still run and
  destroys the WebView of the current view only. Do not use that `Osonai` after `release()`; create a new one.
  After `release()`, a `tool_call` answers `ok: false` with "This Osonai was released." (and logs an error),
  and `send()` and `reset()` are ignored (with a log line).
- `chatView.destroy()` removes and destroys the WebView of one view; its conversation ends.
- When the WebView renderer stops (Android 8 and later), the view removes its WebView and calls `onError`.
  Then `OsonaiChatView.isAlive` is `false`: show a new `OsonaiChatView(context, osonai)`. The conversation is lost.

### An Osonai that lives longer than the Activity (a ViewModel or a singleton)

- The tool functions and the callbacks (`onTurnEnd`, `onClose`, `onOpen`, `onError`) must not capture the Activity
  or its views. Let them use objects that live as long as the `Osonai` (the API client, a repository), or set
  them again in each `onCreate`. Otherwise the `Osonai` keeps the old Activity and calls into it.
- Each new Activity shows a new `OsonaiChatView`; a new view starts a new conversation.
- `release()` destroys only the current view. So call `destroy()` on the Activity's chat view in its
  `onDestroy`, and `release()` in the ViewModel's `onCleared`:

```kotlin
class ChatViewModel : ViewModel() {
    val osonai = Osonai(config).apply {
        tool("view_cart") { api.getCart() }   // api lives as long as the ViewModel, not the Activity
    }
    override fun onCleared() = osonai.release()
}

class ChatActivity : AppCompatActivity() {
    private val vm: ChatViewModel by viewModels()
    private var chat: OsonaiChatView? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        vm.osonai.onClose = { finish() }       // set again: the old Activity is gone
        chat = OsonaiChatView(this, vm.osonai)
        setContentView(FrameLayout(this).apply { fitsSystemWindows = true; addView(chat) })
    }

    override fun onDestroy() {
        chat?.destroy()                        // release() in onCleared does not reach this view
        super.onDestroy()
    }
}
```

A tool function is a `suspend (JSONObject) -> Any?`:

- It runs on the main thread, in a coroutine scope of the `Osonai`. Only `release()` cancels it, not `Close` or
  a view that leaves the window. Do blocking work in `withContext(Dispatchers.IO)`.
- It returns any JSON value: `JSONObject`, `JSONArray`, `Map`, `List`, `String`, a number, `Boolean` or `null`.
- A throw answers the model with `ok: false` and the exception message. Write the message for the model,
  for example "No product given. Ask the user which product." Every `Throwable` counts, also an `Error`
  such as `TODO()` (`NotImplementedError`) and a `CancellationException` of the function's own `withTimeout`.
- A tool name with no function, or no tool name, answers `ok: false`. A result that is not JSON (a `NaN` or
  infinite number) answers `ok: false`. Each `tool_call` gets exactly one answer; a `tool_call` with no `id`
  cannot be answered and is ignored (with a log line).

The test app (`examples/shop/android/app/src/main/java/ai/osonai/shop/android/MainActivity.kt`) registers all
nine tools of the Bozor manifest and opens the chat from every screen.

## Config

| `OsonaiConfig` field | Type | Default | Meaning |
|---|---|---|---|
| `runtimeUrl` | `String` | required | the Osonai server, for example `https://osonai.example.com` |
| `appKey` | `String` | required | the app's publishable key, sent as `Authorization: Bearer` |
| `manifestJson` | `String` | required | the text of the host app's `harness/manifest.json`; a bad JSON text throws in the `Osonai` constructor |
| `title` | `String?` | `"Assistant"` | the header text |
| `greeting` | `String?` | none | the first assistant bubble |
| `suggestions` | `List<String>` | empty | tappable chips under the greeting |
| `placeholder` | `String?` | `"Type a message"` | the input placeholder |
| `strings` | `Map<String, String>` | empty | replaces built-in texts of the chat screen by key, for example `mapOf("notNow" to "Hozir emas")`; the keys are in `STRINGS` in `packages/embed/src/ui.ts` |
| `theme` | `OsonaiTheme?` | none | `primary`: a CSS color; `mode`: `LIGHT`, `DARK` or `SYSTEM` |
| `showClose` | `Boolean` | `false` | show the `Close` button; a tap calls `onClose` |
| `debug` | `Boolean` | `false` | the page sends its trace lines; they go to logcat with the tag `Osonai` |
| `userIdStore` | `UserIdStore?` | `null` (SharedPreferences, `PrefsUserIdStore`) | keeps the user id the Osonai server issued to this install ([docs/mobile.md](../../docs/mobile.md#user-identity)); pass your own to keep it elsewhere |

| `Osonai` member | Meaning |
|---|---|
| `tool(name) { args -> ... }` | registers the host app function for a tool; register every tool before the chat view loads |
| `context` | `Map<String, Any?>` of what is on screen; an open chat gets each new value at once |
| `send(text)`, `reset()` | send a user message; start a new conversation |
| `release()` | end the chat: cancel the running tool functions, destroy the current view's WebView |
| `onTurnEnd(text, tools)` | a turn finished; refresh your screens |
| `onClose()` | the user tapped `Close` |
| `onOpen(kind, id)` | the user tapped a chat card whose manifest view has `open`, for example `("product", "p_101")`; open your own screen for it |
| `onError(message)` | the chat could not connect to the Osonai server, or a turn failed |

| `OsonaiChatView` member | Meaning |
|---|---|
| `OsonaiChatView(context, osonai)` | a new chat screen for `osonai`; it becomes the current view and starts a new conversation |
| `destroy()` | remove and destroy this view's WebView; call it in `onDestroy` when the `Osonai` outlives the Activity |
| `isAlive` | `false` after `destroy()`, after `release()` or after the WebView renderer stopped |

`OsonaiChatView(context, osonai)` turns on WebView remote debugging (`chrome://inspect`) only when the host app
is debuggable. The page cannot navigate away from the chat bundle, so the JavaScript bridge `OsonaiAndroid` is
never exposed to another page. The library's consumer R8 rules keep the bridge method.

## Known limits

- Published on JitPack only, not on Maven Central yet.
- The view does not apply window insets. Give it the area between the system bars and above the keyboard:
  `fitsSystemWindows = true` on its parent (what the test app does; with targetSdk 35 Android 15 draws
  edge to edge) and `android:windowSoftInputMode="adjustResize"`. With these two settings the input stays
  above the soft keyboard on the Android 15 emulator.
- One `OsonaiChatView` per `Osonai` at a time: a new view takes over the bridge.
- The page reads `init` once. A new config needs a new `Osonai` and a new view.
- Maestro on Android sees the chat's texts and the enabled state of `Send`, but not the HTML ids
  (`osonai-input`, `osonai-send`): match on the texts. The soft keyboard's action key is also named `Send`,
  so limit the selector to the page: `childOf: {text: "Osonai chat"}` (the page title).
- `minSdk` 24 is set but only Android 15 (API 35, WebView 124) is tested.
